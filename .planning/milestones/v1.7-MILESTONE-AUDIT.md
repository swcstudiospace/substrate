## 1. The owner's two questions

### 1.1 Live Steering (phase 67): PARTIAL in delivery

**Plain answer:** the steering system is built and tested, but no running agent session reads its messages yet, and no one has shown a message reaching a real session. The gap is installation and wiring, not code.

**What works (in code, tested with fake servers and stores):**
- `substrate steer` works over REST routes that carry the same audit, admission and operator guard as the MCP tools. An operator can list sessions and their state, queue a directive, acknowledge it, and listen for directives. Agents cannot author directives.
- `session_context` returns a bounded, redacted digest of the other live sessions of the caller's repository, with the source and age of each item.
- `memory_brief` gets sessions, steering and handoff sections behind `SUBSTRATE_BRIEF_SESSIONS`.
- Session state can be kept in the `steering_sessions` table (opt-in). It survives a restart, and TTL and cap are enforced.
- `GET /steering/wait` long-polls for a directive with a bounded timeout, so a session need not poll `docs_search`.
- The `checkpoint_hint` reader in `substrate session hook` writes the checkpoint a directive names. The context trigger prints the digest.
- PR #192 (2026-10-30) removes a session's live steering state when the session ends, authorised by its surface.

**What needs an operator (not done):**
- Install the printed steering and context hook configuration (`substrate session hook-config`) in each host that runs sessions. ADR 0007 maps no host event to these two triggers, so nothing fires them today.
- Enable `SUBSTRATE_PLANNING_STEERING`, `SUBSTRATE_PLANNING_STEERING_PRINCIPALS` (the operator tokens' surfaces), `SUBSTRATE_BRIEF_SESSIONS` and `SUBSTRATE_STEERING_SESSIONS_TABLE`. Issue the operator tokens.
- Decide on `SUBSTRATE_PLANNING_STEERING_AUDIT_TABLE`. Without it the directive inbox is memory-only, and a restart forgets queued directives.

**What does not work yet:**
- No live delivery to a real session has been shown. The record says so (`67-VERIFICATION.md`, residual risks; `docs/live-steering.md`).
- A directive acknowledged before a restart comes back with `checkpoint_hint: null`, so the hook writes no checkpoint for it. The audit table keeps no transition result.
- The combined brief has not been proved to stay inside its byte cap with the live sections present (criterion 3, PARTIAL).
- A stale session stays listed in the digest until its age says so.

### 1.2 Worktree multi-session support (phase 68): PARTIAL

**Plain answer:** the fleet tooling works and is safe in the cases it covers. Five of its six criteria are met in code, with caveats. The sixth is PARTIAL: the dispatcher ignores the roots variable. Nothing runs the tooling on a schedule, so the registry is only as current as the last manual run, and the registry itself is off by default. Several safety edges are open.

**What works (confirmed in code on `origin/main`, per `68-VERIFICATION.md`):**
- Discovery uses git, not a path convention: `git worktree list --porcelain -z` from every repository under the roots, including linked worktrees outside them. `worktree-graph.ts` reads `SUBSTRATE_WORKTREE_ROOTS` and falls back to the old hard-coded root only when no absolute entry is set.
- The registry route `POST /worktrees/report` stores path, repo, branch, head, base, dirty state, ahead and behind, last commit time, size, session and graph attribution, and PR state into the `worktrees` table (migration steps 36, 40 and 41). The route answers 503 while `SUBSTRATE_WORKTREE_REGISTRY` is off, which is the default.
- Prune classifies each worktree as `safe`, `review` or `never`. Only `safe` is removed, after its identity is reloaded from git and its claim is asked again. Removal is `git worktree remove` without `--force`, and it writes one ledger note per removal. A branch that gained commits after its PR merged is `review`.
- Ignored files that hold work count as `review`, so `--execute` does not remove them.
- `conflicts` lists overlapping pairs, predicts textual conflicts with `git merge-tree --write-tree` (git 2.38 or newer; an older git reports unavailable), and prints a suggested merge order.
- The disk floor, `SUBSTRATE_WORKTREE_MIN_FREE_GB` (default 5 GiB), is enforced by `substrate worktree provision`, and the refusal comes before any git command.
- The brief names other sessions' worktrees that touch the same files (PR #185). PR #189 leaves out a clean merged or closed row, but keeps one that has uncommitted work.
- `guard` (PR #188) is read-only. It refuses on any probe failure, refuses symbolic links without reading their targets, and refuses a primary checkout or a `.planning/` directory inside the workspace.
- `merge-back` (PR #193) never deletes. It writes one `worktree.merge_back` note per eligible worktree and refuses a primary checkout. The dry run is the default.
- Doctor reports a checkout behind origin's default branch, report-only (PR #190).

**What does not work, or is open:**
- **Criterion 1 is PARTIAL.** The dispatcher never reads `SUBSTRATE_WORKTREE_ROOTS`. It creates under one fixed root, and its disk floor checks free space on `/` only.
- **No scheduler.** Nothing in the repository runs `substrate worktree scan --report` on a timer or hook. The registry, the brief section and the claims lookup are only as fresh as the last manual run.
- **The guard has no caller.** Only `substrate worktree guard DIR` reaches it. No workspace-removal path in the repository calls it.
- **Merge-back race.** `merge-back` narrows the check-then-note race but does not close it. Its reload compares HEAD, branch and detached state, not cleanliness, so an edit between the dirty check and the note is not seen.
- **Prune's last check and removal are separate steps.** Ignored files written in between are removed with the worktree, because `git worktree remove` deletes ignored files without asking.
- **Local-only repository.** Where a repository has no origin, merged status trusts local ancestry. No test covers a repository with no origin at all.
- **Dependence on `gh` and git.** Without `gh`, `pr_state` is `unknown`, so a squash-merged branch reads `review`. That fails safe, but it is reported as unprovable. The git 2.38 requirement was not checked on any host.
- **Commit messages.** 8f1ce16c says "migration 35" (it is 36) and names a `worktrees_report` tool that does not exist. Its squash subject, like #187 to #192, is the truncated line in section 5.
