## Residual risks

- Server key retention: `planning/presence-dragonfly.ts:33-35` sets `EX` to 86400 + 3600 s, so Dragonfly removes a session key about 25 h after its last heartbeat. This is server retention, not a code deletion (CONTEXT, SC2 residual).
- Changed meaning of `active`: the observer heartbeats a checkout only when it sees a complete change in it (`observer.ts:142`). `active` now means "changed a planning document within the freshness window", not "is alive". A quiet session reads `stale`. Documented in CONTEXT and `mcp.ts:1427`.
- Stat-fingerprint reuse: a same-size edit that lands within filesystem timestamp resolution after the previous scan keeps its stored hash until the next write changes ctime (`index.ts` reuse rule, CONTEXT residual). Nanosecond timestamps make the window negligible on the Linux filesystems used.
- Absolute path disclosure: heartbeats store `worktree: root` (`observer.ts` heartbeat record) and `planning_sessions` returns it to any MCP caller.
- Process-local baseline and index cache: a restart resets both, so changes made while the process was down are not published.
