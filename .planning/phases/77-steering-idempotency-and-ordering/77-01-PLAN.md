# Phase 77 — Steering idempotency and ordering (PLAN, revision 3: durable)

Branch `gsd/v18-p77-steering-idempotency`, stacked on phase 71. Revision 1 kept replay and sequence in process memory.
Revision 2 (owner request) makes both durable in the steering store, so a retry across a restart replays and sequence order survives a restart.

## 1. Discovery (grep, confirmed in revision 1)

- No steering route or MCP tool carried an idempotency key or a sequence number. `docs/live-steering.md` said queue and ack were unkeyed.
- `SteeringInbox` kept a single global `lastSequence` (internal, read through `sequenceOf` and `queuedFor`).
- `queueSteering` minted a fresh `randomUUID()` per call, so a retried queue wrote a second directive.
- Neighbour precedents: RAG replay cache (TTL and cap, in memory, `mcp.ts`), `IDEMPOTENCY_KEY_PATTERN` (`event.ts`), the audit sink's
  transactional `sql.begin` use (`steering-sessions-store.ts`).

## 2. Decisions

D1 **Key field.** Optional `idempotency_key` on the REST queue body and the MCP `steering_queue` input. Grammar
`IDEMPOTENCY_KEY_PATTERN` (8–128 of `[A-Za-z0-9._:-]`).

D2 **Scope.** A replay is matched on `(author principal, target session, key)`. The author is the caller's surface. A key from
another surface or for another target session is a fresh command.

D3 **Durable replay store.** Table `planning_steering_replay` (migration 43, opt-in `steering-audit`, expand, reversible):
`scope_key` primary key, `target_session_id`, `fingerprint`, `directive_json`, `sequence`, `queued_at_ms`, `expires_at_ms`.
Retention `SUBSTRATE_PLANNING_STEERING_IDEMPOTENCY_TTL_S` (default 86400 s, bounds 60..2592000). Capacity
`SUBSTRATE_PLANNING_STEERING_IDEMPOTENCY_CAP` (default 10000, bounds 1..1000000). A save runs in one transaction: prune expired
records, insert unless a live record holds the key, then delete the oldest beyond the cap. Only accepted queues are stored.

D4 **Replay path.** Under the inbox lock, after validation and authorisation, before duplicate, rate and audit checks. A live
record with the same fingerprint returns the original queued record (same directive, queued time, sequence): no audit append,
no rate token, no state change. A live record with a different fingerprint is `idempotency-conflict` (409).

D5 **After retention.** An expired record is not live. The same key is then a new command with a new id and sequence.

D6 **Restart.** Closed by D3 and D7. A keyed retry after a restart, within retention, replays. Revision 1 listed this as a risk.

D7 **Durable sequence.** Table `planning_steering_sequence` (`target_session_id` primary key, `last_sequence`). A queue takes its
number with one upsert `returning`, before the audit row, so two processes never take the same number. The number is stored on
the queued audit row in a new nullable column `planning_steering_audit.delivery_sequence` (migration 43; a NULL keeps the row's payload
hash). Restore reads each directive's stored number and advances the counter past it. A row written without a number takes the
session's next. A failed audit leaves a gap in the counter, never a reuse.

D8 **Wake-up only for a fresh queue.** `enqueueReceipt` tells the caller whether the queue was a replay. `queueSteering` calls the wiring hook `onQueued` (the service's `onSteeringQueued`: waiters released, one hint announced) only for a fresh queue. A replay wakes nothing and emits nothing, so a retry across a restart cannot re-announce. The route and the MCP tool no longer call the hook themselves.

D9 **Wait delivery carries the sequence.** Unchanged from revision 1: `nextQueuedDirective` returns `{ sequence, record }`.

D10 **Errors.** `idempotency-conflict` is 409. A store read or write failure on the queue path is `audit-unavailable` (503), never
a silent fallback.

D11 **Replay claim and audit in one transaction.** The keyed claim is written inside the same `sql.begin` as the audit row (`claimReplay` in `steering-store.ts`): the claim is `insert ... on conflict (scope_key) do nothing`, the audit write runs inside it, and a refused audit rolls the claim back. The queue is accepted only after that commit, so a reply lost after commit replays on retry and a refused audit queues nothing. A store failure on the claim is `audit-unavailable` (503), never a silent queue. The memory store has no transaction. Revision 3 (verification H6) replaces the earlier "replay save after audit, failure reported on stderr" decision. See R1.

D12 **Ports and wiring.** `SteeringIdempotencyStore` is injected through `SteeringInboxDeps.store`. Production passes
`bunSteeringIdempotencyStore` (`steering-store.ts`) from `IndexStore.steeringIdempotency()`, under the same opt-in as the audit sink.
Without it the inbox uses `MemorySteeringIdempotencyStore`. Settings come from `loadSteeringIdempotencySettings` (`steering.ts`), are
included in `steeringErrors`, and a bad value answers `misconfigured`.

D13 **Docs.** `docs/live-steering.md` line 33 states the durable keys, sequence, both settings, and the bounds.

## 4. Acceptance mapping

| Criterion | Proof |
|---|---|
| 1. Replayed keyed command returns original, writes nothing | inbox replay (append count, rate); restart replay (insert attempts unchanged); tool replay; hint emit count |
| 2. Unkeyed unchanged | unkeyed reply key set; unkeyed repeats are two directives; unkeyed sequence now durable but not in the reply |
| 3. Keyed reply exposes sequence; replay same; distinct in order; restDirective and wait expose it; order survives restart | keyed reply sequence; replay equal; waiter order; restart sequence continues from stored counter and restored numbers are kept |

Scope (D2) and retention (D5) are tested at the inbox and across restart.

## 5. Open risks (after revision 2)

- R1 Crash between the audit row commit and the replay claim: closed on the Postgres keyed path, which commits the audit row and the claim in one `sql.begin` (D11). Not behaviour-verified here: `steering-idempotency.pg.test.ts` (`:93`, `:112`) has only orchestrator per-file evidence that predates 4b84e50c (77-VERIFICATION.md, T6). The memory store has no transaction and no durability across restart.
- R2 A failed audit leaves a gap in the counter (no reuse). Order is unaffected.
- R3 The Bun SQL adapter and migration 43 were not executed here (no database in this environment). They need a Postgres run
  before merge. The restart tests use `MemorySteeringIdempotencyStore` as the durable stand-in.
- R4 At capacity the oldest key is forgotten before retention. Steady use (10 per minute per session by default) keeps load low.
- R5 The directive read shape gains `sequence` for unkeyed directives too. The unkeyed command reply is unchanged.
- R6 Every queue now takes the counter with one upsert (when the audit opt-in is on).
