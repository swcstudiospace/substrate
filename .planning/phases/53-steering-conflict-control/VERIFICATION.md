## Residual risks

- **Per-process announcement set (SC2 limit).** The announced-conflict set is per process (`observer.ts:129`). Each checkout's server announces its own copy of a conflict in its repository, so two servers observing the same conflict each emit one `planning.conflict` event. The ledger holds two rows for one conflict, and no cross-server key prevents that.
- **Store-level-only SC4 proof.** The durable store and its reopen tests prove restart behaviour inside one process (`checkpoint-store.test.ts:34-45`, `:110-121`). No test kills a process mid-write. The reread-then-write in `putIfAbsent` (`checkpoint-store.ts:66-71`) is serialised per instance (`checkpoint-store.ts:93-100`), not across instances, so concurrent inserts through two open instances in one process are not covered by a test. The header (`checkpoint-store.ts:12-13`) says the store takes no lock across processes.
- **No production caller of recordCompletion (SC4).** Nothing outside tests calls `recordCompletion` (`checkpoint.ts:71`) or `DurableCompletionStore.open` (`checkpoint-store.ts:58`). The plan-step executor is outside this repo. `service.ts` uses only `completionStoreView`, which reports `durable: true` whenever the directory is set.
- **Write gate with no caller.** `gateConflictSensitiveWrite` (`conflicts.ts:112`) has no production caller. Its only callers are in `conflicts.test.ts`. This repo has no conflict-sensitive write path. See the decision below.
- **Steering directives are in memory.** `SteeringInbox` keeps its records in a `Map` (`steering.ts:171`). The durable directive store (PLAN W2) is not built. A restart loses queued and acknowledged directives, though their audit rows persist when the sink is live. The conflict flag is also caller-supplied (`steering-tools.ts:167`, `steering.ts:81`), so the confirm rule at `steering.ts:261-263` trusts the caller's flag rather than `detectConflicts`.
- **The watcher gap is scan-based (SC3 limit).** The repo has no filesystem watch. A gap is an incomplete scan (`report.ts:33-34`), so an event missed between scans is not seen until a scan finds the drift.
- **Truncated listings keep open conflicts open without re-checking them.** `observer.ts:356` keeps every open signature when the listing is truncated, so a conflict that actually cleared behind the truncation stays in the set until a complete listing shows it gone. That suppresses a repeat warning and never invents one.

## Decision: SC3 and the gate caller

SC3 as written says only that a watcher gap marks the session view unknown until a complete scan. It names no write. The decision is that SC3 does not require a production caller for `gateConflictSensitiveWrite`. The view is the criterion, and it is unknown in production (`observer.test.ts:346`, `:372`). This repo has no conflict-sensitive write path, and adding a caller would invent one, which the phase CONTEXT excludes. The missing caller is a residual. The first conflict-sensitive write added later must call the gate.
