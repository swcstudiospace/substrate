## Residual risks

- **Cross-checkout duplicate announcements (SC2 limit).** The announced-conflict set is per process (`observer.ts:91`). Two checkouts whose servers both observe the same conflict each emit one `planning.conflict` event for it. The ledger holds two rows for one conflict, and no cross-server key prevents that.
- **`gateConflictSensitiveWrite` has no production caller (SC3 residual).** Its only callers are in `conflicts.ts:100` and `conflicts.test.ts`. This repo has no conflict-sensitive write path. See the decision below.
- **Steering's conflict flag is caller-supplied.** `conflictsWithActivePlan` comes from the request (`steering-tools.ts:167`, `steering.ts:81`). The confirm rule at `steering.ts:261-263` therefore trusts the caller's flag. It is not fed from `detectConflicts`.
- **No production writer of completions (SC4 residual).** Nothing outside tests calls `recordCompletion` (`checkpoint.ts:71`) or `DurableCompletionStore.open` (`checkpoint-store.ts:57`). `service.ts:1456` uses only `completionStoreView`, which reports `durable: true` whenever the directory is set. The plan-step executor is outside this repo.
- **Reopen is not a process kill (SC4 limit).** `checkpoint-store.test.ts:34` simulates the restart with a second store instance. No test kills a process mid-write. The atomic rename (`checkpoint-store.ts:101`) is the crash-safety argument, and it is not exercised by a crash test.
- **The watcher gap is scan-based (SC3 limit).** The repo has no filesystem watch. A gap is an incomplete scan (`report.ts:33-34`), so an event missed between scans is not seen until a scan finds the drift.
- **Steering directives are held in memory.** `steering.ts:171` holds the records in a `Map`. The durable directive store (PLAN W2) is not built. A restart loses queued directives, although their audit rows persist when the sink is live.

## Decision: SC3 and the gate caller

SC3 as written says only that a watcher gap marks the session view unknown until a complete scan. It names no write. I decided that SC3 does not require a production caller for `gateConflictSensitiveWrite`. The view is the criterion, and the view is unknown in production (`observer.test.ts:311`, `observer.test.ts:337`). This repo has no conflict-sensitive write path. Adding a caller would mean inventing a write path, which the phase CONTEXT excludes. The missing caller is recorded as a residual, and the first conflict-sensitive write added later must call the gate.
