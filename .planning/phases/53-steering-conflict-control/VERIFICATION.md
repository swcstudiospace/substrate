## Residual risks

- **Per-process announcement set (SC2 limit).** The announced-conflict set is per process (`observer.ts:108`). Two checkouts whose servers both observe the same conflict each emit one `planning.conflict` event. The ledger holds two rows for one conflict, and no cross-server key prevents that.
- **Write gate with no caller (SC3 residual).** `gateConflictSensitiveWrite` (`conflicts.ts:100`) has no production caller. Its only callers are in `conflicts.test.ts`. This repo has no conflict-sensitive write path. See the decision below.
- **Store-level-only SC4 proof.** The durable store and its reopen test prove restart behaviour inside one process (`checkpoint-store.test.ts:34-45`). No test kills a process mid-write, and nothing outside tests calls `recordCompletion` (`checkpoint.ts:71`) or `DurableCompletionStore.open` (`checkpoint-store.ts:57`). `service.ts` uses only `completionStoreView`, which reports `durable: true` whenever the directory is set. The plan-step executor is outside this repo.
- **Steering directives are in memory.** `SteeringInbox` keeps its records in a `Map` (`steering.ts:171`). The durable directive store (PLAN W2) is not built. A restart loses queued and acknowledged directives, though their audit rows persist when the sink is live. The conflict flag is also caller-supplied (`steering-tools.ts:167`, `steering.ts:81`), so the confirm rule at `steering.ts:261-263` trusts the caller's flag rather than `detectConflicts`.
- **Cadence is asserted by delay, not by a tick.** `observer.test.ts:196-222` asserts the delay passed to `setInterval` (15000 ms unset, 2500 ms set through `SUBSTRATE_PLANNING_SCAN_INTERVAL_MS`) and that `start()` takes no argument. The captured callback (`observer.test.ts:206`, `_run`) is never invoked. The link from the tick to `scan()` is `observer.ts:124` (`() => void this.scan()`), read but not exercised.
- **The watcher gap is scan-based (SC3 limit).** The repo has no filesystem watch. A gap is an incomplete scan (`report.ts:33-34`), so an event missed between scans is not seen until a scan finds the drift.

## Decision: SC3 and the gate caller

SC3 as written says only that a watcher gap marks the session view unknown until a complete scan. It names no write. The decision is that SC3 does not require a production caller for `gateConflictSensitiveWrite`. The view is the criterion, and it is unknown in production (`observer.test.ts:345`, `:371`). This repo has no conflict-sensitive write path, and adding a caller would invent one, which the phase CONTEXT excludes. The missing caller is a residual. The first conflict-sensitive write added later must call the gate.
