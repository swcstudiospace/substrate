# Phase 65: Doc Watch - Context

**Gathered:** 2026-10-29 (Run 14)
**Status:** Decisions fixed by the orchestrator from the Run 14 scout evidence; the owner's request is in `.planning/STATE.md` (Run 14).

## Phase boundary
Triggers, coalescing and the sync command that connect a documentation change to the phase 63 bulk path, with state that survives restarts. It does not decide what is worth retrieving.

## Decisions
- **D65-1:** four triggers feed one idempotent sync: git hooks, a filesystem watcher, the reconcile timer and the server's own planning events. Existing mechanisms: the post-commit collector is the only git hook that ships (`packages/collectors/src/install-git-hook.ts:16-17`, never overwrites a foreign hook, no debounce, emits the first 20 changed file names); the planning observer scans `.planning/` of one checkout every 15 s (`planning/observer.ts`, `planning/config.ts:22`); the server refresh runs only when `docsBackend === "lightrag"` (`service.ts:5651`).
- **D65-2:** the server's in-memory `planningHashes` is replaced by the manifest, so a restart re-ingests nothing unchanged.
- **D65-3:** `POST /docs/merge-trigger` has local sources for two datasets and nothing calls it for `agent-substrate` or `programming-desk` (`server.ts:353-361`, `:1736-1812`); it stays for skills sync, and the new path does not depend on it.
- **D65-4:** the VPS is private, so GitHub pushes cannot call it. The reconcile timer runs `git fetch` for each registered repository and then reads the fetched commit's tree directly (`git ls-tree -r` and `git cat-file --batch` on the remote-tracking default branch), because a fetch moves refs and not the checkout: a push made elsewhere leaves the working tree unchanged, so a working-tree scan would keep reporting no change. One view wins per repository per sync, decided from git state alone so the two never alternate on the same `(repo, path)` row: the working tree of the canonical checkout when its HEAD is level with or ahead of the fetched default branch (including uncommitted edits), the fetched tree only when the checkout is strictly behind it (the fetched default branch contains HEAD and has more) and its documentation is unmodified, and the working tree when the two have diverged or when a behind checkout carries uncommitted or unpushed documentation changes, so local notes never disappear from search. A sync that finds the chosen view equal to the manifest changes nothing. The reconcile tests include a remote-only push and a test that alternates local edits and remote-only pushes without pulling and asserts the manifest follows the newer view, with no flip-flop and no re-ingest of an unchanged file.
- **D65-5:** the default triggers write nothing into any repository: the watcher and the reconcile are read-only, and git hooks are an opt-in installer the operator runs for chosen repositories (a hook writes into that repository's `.git`). Hooks and the watcher never fail the user's command; hints are bounded and lost hints are recovered by the reconcile run, which also compares active manifest rows with the docs plane (the manifest and the plane are a dual write, so drift is detected, not assumed away). Staged units carry `Nice`, an idle I/O class, `CPUQuota` and `MemoryMax`, and the watcher falls back to sweep-only when the inotify limit is reached.
- **D65-6:** a new `docs.sync` event maps onto the existing `note` kind through `payload.action` with a row in `event-sources.ts` and the table in `docs/event-vocabulary.md`; the vocabulary lock stays unchanged. The existing `docs.planning` action has no row (`service.ts` only) and gets one.
