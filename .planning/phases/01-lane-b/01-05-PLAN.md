<objective>
Fill in grok-hermes-connector v0.4 — the Grok Bot half of the phase goal.

The connector already reports `v0.4.0` at runtime (`__version__` in
`src/grok_hermes_connector/__init__.py`), but **none of the four tools that
version number was minted for exist yet**, and `pyproject.toml` still declares
`0.3.3`. `handoff_to_hermes` works today as a fire-and-forget Hermes dispatch but
neither accepts nor records a Graph ID. So Phase 1 Success Criterion 5 is new
surface area, not an extension of existing plumbing — the version string is a
target to fill in, not a completed milestone.

Purpose: let Grok Bot read the brief and emit events through the boundary it
already owns. The connector is where the Grok↔Hermes trust boundary, OAuth and
redaction already live, so adding substrate forwarding there is additive rather
than a new boundary.

Output: a `substrate_ext.py` following the repo's own `_ext.py` convention, four
`@mcp.tool` forwarding tools, a `graph_id` parameter on `handoff_to_hermes`, a
one-line version fix, and tests.

This plan expands the slice plan 01-02 proved — same fail-open contract, same
redaction requirement — into the connector's dict-returning house style. Unlike
the Hermes plugin, this repo already declares `httpx`, so `substrate_ext.py` uses
it, matching `github_ext.py` exactly. `redactor.py` is imported directly here; it
is this repo's own module and plan 01-01 put it under version control.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Grok Bot → connector | Already the established untrusted boundary: OAuth, rate limiting and redaction all live here. Agent-authored text arrives as tool arguments. |
| connector → substrate-mcp | Those arguments cross a second process boundary as brief queries, memory writes and event payloads. |
| connector → Hermes dispatch | `handoff_to_hermes` now carries a Graph ID into a background Hermes process. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-05-01 | Information Disclosure | Tool arguments forwarded to `/events` and the memory write | high | mitigate | `substrate_ext.py` applies the repo's own `redact_text` to every string value before the body is serialized; Task 1 test 5 pins it with a `tskey-` style token. No second redaction pass is written. |
| T-01-05-02 | Denial of Service | A tool call hanging behind an unresponsive substrate | high | mitigate | `substrate_ext.py` uses a 1.5s timeout rather than the repo's 15s `_TIMEOUT`, and every failure path returns a dict instead of raising. Task 1 tests 3 and 4 pin both error dicts. |
| T-01-05-03 | Denial of Service | A substrate outage turning a successful handoff into a failure | high | mitigate | The `handoff` emit runs after dispatch succeeds and its outcome is discarded; Task 2 test 4 asserts the handoff result is unchanged when the emit fails. |
| T-01-05-04 | Tampering | Existing `handoff_to_hermes` callers | medium | mitigate | `graph_id` is optional with a `None` default, following the existing `tenant` style; Task 2 test 3 asserts a call omitting it behaves exactly as today. |
| T-01-05-05 | Spoofing | Unauthenticated POST to 127.0.0.1:7410 | medium | mitigate | `SUBSTRATE_TOKEN` bearer header when set; loopback-only substrate; the connector opens no new listener and its own `Bearer CONNECTOR_TOKEN` surface is unchanged. |
| T-01-05-06 | Repudiation | Handoffs with no traceable Graph ID | medium | mitigate | `graph_id` is threaded into `store.update_meta` and into the `span` context, and emitted as a `handoff` event, so a handoff becomes attributable rather than fire-and-forget. |
| T-01-05-SC | Tampering | npm/pip/cargo installs | low | accept | No install runs: `httpx` is already a declared dependency of this repo and `redactor.py` is its own module, brought under version control by plan 01-01. |
</threat_model>
