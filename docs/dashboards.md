# SLO dashboards as code (uplift-5 S6)

`infra/vps/dashboards/` holds two Grafana dashboards and two provisioning examples.
They are generated by `scripts/dashboards.ts` from the same code the running server
judges itself with, and a test fails when they drift from it. Nothing here installs
Grafana, a plugin or a datasource: those are operator steps (below), and the repo
carries no token, URL or hostname of ours.

## Where the data comes from

Only `GET /slo/history?series=&window=&step=` (uplift-4 S6, see
[`observability.md`](observability.md) § Durable metrics history). It is the one feed
there is: `/metrics` is JSON rather than Prometheus text, and the OTLP exporter has no
sink. The route

- is bearer-gated exactly like `/slo` (unless `SUBSTRATE_ALLOW_ANONYMOUS=1`);
- answers `404 {"enabled":false}` until `SUBSTRATE_METRICS_HISTORY=on` **and** the event
  ledger is configured, so every panel is empty until the history has been on for one
  sampling interval;
- returns at most 2000 points per request and keeps 14 days by default
  (`SUBSTRATE_METRICS_HISTORY_TTL`), so the dashboard windows stop at `14d`.

The datasource is [Grafana Infinity](https://grafana.com/grafana/plugins/yesoreyeram-infinity-datasource/)
(JSON over HTTP). Every panel is one request: `series`, `window` and `step` are the
route's own query parameters, with `window` and `step` taken from two dashboard
variables (`1h`..`14d`, `1m`..`1h`, default `24h` and `5m`). The route raises a step
that would exceed 2000 points, so a long window shows coarser buckets; the `stepS` in
the answer is the step it really ran at. **The dashboard time range is separate from
the `window` variable**: both dashboards open on `now-24h`, and a panel draws only the
points inside the time picker's range, so a `window` above `24h` is clipped to 24 h
until the time picker is widened to match.

**Load.** Each chart panel is its own `/slo/history` request (7 on the SLO dashboard,
12 on the data-planes one), and the route runs at most 16 reads at once
(`HISTORY_PENDING_MAX`) through the shared ledger breaker, with each request key
memoised for 15 s. Both dashboards therefore refresh every `5m`, not faster. Opening
both at once on a cold cache can ask for up to 19 distinct reads; the ones past the cap
are answered `503 {"enabled":true,"busy":true}` with `Retry-After: 5`, which shows as an
error on those panels until the next refresh. Open one dashboard at a time, or reload,
if you see it.

## Files

| File | What it is |
| --- | --- |
| `infra/vps/dashboards/substrate-slo.json` | Dashboard `substrate-slo`: one panel per catalogue objective, docs search latency, plane availability, cache hit ratio, admission decisions, capacity runway |
| `infra/vps/dashboards/substrate-data-planes.json` | Dashboard `substrate-data-planes`: brief p50, emit p95, plane p95, docs outcomes, and the extended-series panels |
| `infra/vps/dashboards/provisioning/datasources.yaml.example` | The Infinity datasource, uid `substrate-slo-history`; URL and bearer are `${SUBSTRATE_DASHBOARD_URL}` and `${SUBSTRATE_DASHBOARD_BEARER}` |
| `infra/vps/dashboards/provisioning/dashboards.yaml.example` | A file provider that loads the two JSON files from a directory |

The two placeholder names are interpolated by Grafana from **its own** environment.
They are names, not values: the substrate base URL and a substrate surface bearer
belong in the environment file of the Grafana unit, never in the provisioning file or
the repository.

## Panels and series

Every threshold line is the target of the matching objective at the catalogue
defaults (`sloCatalogue()`, `docsSearchObjective()`, `DEFAULT_THRESHOLDS`); a
`SUBSTRATE_SLO_*` override on the server is **not** reflected, because the generator
cannot read the server's environment. The live `GET /slo` is what judges a breach;
a panel shows stored history against the default line.

The units and the one label of each series (a line per `surface`, `plane`, `decision`,
`outcome`, `result` or `mode`) come from the series' own spec in
`packages/mcp-server/src/metrics-history.ts`. The extended panels are in the committed
JSON whether or not the server runs `extended`: with `core` the route answers `400`
for their series, and those panels show the datasource's error instead of data. A panel is left out of the generated
file only when its series is missing from the allow-list the generator is given.

## Core and extended series

`SUBSTRATE_METRICS_HISTORY_SERIES=core|extended` (default `core`) picks the allow-list
the sampler writes and `/slo/history` serves.

- `core` is the original 11 series, and `planning.transition` (phase 54), written once per detected planning change rather than
  sampled. With the variable unset, empty or `core`, the sampler and its rows are those of uplift-4 S6; the route also serves the
  transition series, which is empty until a planning change is seen.
- `extended` adds the evidence the promotion advisor reads. All are read from
  instruments that already exist; counters are the interval's delta (reset-safe),
  gauges are the reading at the sample.

| Extended series | Kind | Label | Meaning |
| --- | --- | --- | --- |
| `cache.operations` | counter | `result` (hit, miss, bypass, error, coalesced, stale, refresh, would_serve_stale) | All key classes summed, one label only. `would_serve_stale` is counted only for the brief class under `SUBSTRATE_CACHE_SWR=shadow`, so a ratio such as `would_serve_stale / miss` has a brief-only numerator over an all-class denominator: **it is a lower bound** on the brief's own share |
| `brief.profile_bytes_saved` | counter | none | Bytes the compact brief profile would save (full minus compact), fresh answers in shadow or enforce |
| `brief.recall` | counter | `result` (included, would_include, cold, stale, disabled, dropped_by_cap) | Briefs by what they did with the recall snapshot |
| `recall.prefetch` | counter | `result` (ok, empty, error, skipped_breaker, skipped_unconfigured, skipped_cache) | Recall snapshot refreshes |
| `memory.expired` | counter | `mode` (served, hidden) | Expired memory entries an index read met |
| `hindsight.outbox_size` | gauge | none | Parked retain forwards; the worst reading in a step |
| `hindsight.outbox_oldest_age_s` | gauge | none | Age of the oldest parked forward; 0 when empty |
| `index.archive_age_s` | gauge | none | Age of the newest complete index archive; no row until a first archive exists |
| `endpoint.proxy_planes` | gauge | none | Data planes whose endpoint is a configured proxy, set at boot; a count, with no address |

Admission needs no new series: `admission.decisions` already carries `limited` and
`shadow_limited`. The ledger client can store and read an extended series whatever the
mode; **only the route and the sampler follow the mode**, so changing the variable back
to `core` stops the writes and the reads at once and leaves the rows to expire on the
TTL. An unknown value is `core` and one config warning at boot names the variable.

### Row growth

The history table has a 14-day TTL (`SUBSTRATE_METRICS_HISTORY_TTL`) and an unresolved
volume size: **500 MB** is recorded in one place and **5 GB** in the plan. That is why
`extended` is opt-in. These are estimates from the series count, not measurements; no
row size has been measured.

| Interval at 60 s | Rows per interval | Rows per day |
| --- | --- | --- |
| Core (existing estimate) | 20 to 30 | about 29 000 to 43 000 |
| Extended, added: the gauges alone (an idle interval) | 2 to 3 | about 2 900 to 4 300 |
| Extended, added: gauges plus normal counter activity | 10 to 17 | about 14 400 to 24 500 |
| Extended, added: every result of every counter active, plus the gauges | 26 | 37 440 |

Over 14 days the typical extended total is therefore roughly 0.6 to 0.95 million rows
against roughly 0.4 to 0.6 million for core. The worst case for one interval, core plus
extended with every label active, is **104 rows** (core 78: 28 surface rows each for
`brief.p50` and `brief.p95`, 5 planes each for `plane.availability` and `plane.p95`,
4 admission decisions, 3 docs outcomes and 5 single rows; extended 26: 8 cache results,
1 bytes-saved, 6 recall results, 6 prefetch results, 2 expiry modes, 3 gauges), well
under the 200-row batch cap. A test sums that bound from the series specs, so a new
series or label that breaks it fails the suite. Read the
real figure from the ledger's `capacity` read (`/healthz`) after a day of running, and
confirm the volume, before turning `extended` on or raising the TTL.

## Operator steps

None of these is run by code or by the test suite.

1. **Turn the history on** in `/etc/substrate/substrate.env`: `SUBSTRATE_METRICS_HISTORY=on`
   (needs the event ledger). For the promotion evidence and the data-planes extended
   panels also set `SUBSTRATE_METRICS_HISTORY_SERIES=extended`, after the row-growth
   figures above have been checked against the volume. Restart `substrate-mcp`. Boot
   prints `metrics history: every <n> s, ttl <t>` (with `, extended series` when set).
2. **Install the Infinity plugin** on the Grafana host (`grafana-cli plugins install
   yesoreyeram-infinity-datasource`, or the equivalent for the container). Where Grafana
   runs, and whether the host can spare the memory, is not decided by this repository.
3. **Give Grafana the two values** in the environment file of its unit, root-readable
   only: `SUBSTRATE_DASHBOARD_URL` (the substrate base URL as Grafana reaches it,
   **without a trailing slash**: the panels append `/slo/history`) and
   `SUBSTRATE_DASHBOARD_BEARER`. The substrate has no read-only or scoped token: a
   bearer is an ordinary `SUBSTRATE_TOKEN_<SURFACE>` token with that surface's full
   authority. Give Grafana its own surface token (so it can be revoked on its own),
   keep it only in that env file, and treat the file as holding a full credential.
4. **Provision**: copy `provisioning/datasources.yaml.example` to Grafana's
   `provisioning/datasources/`, `provisioning/dashboards.yaml.example` to
   `provisioning/dashboards/` (edit its `path`), and the two `*.json` files to that
   path; restart Grafana.
5. **Check** one panel: open a dashboard and look at a panel (a `404` or an error
   panel means the history is off, the bearer is wrong or the URL is), or run
   `curl -s -H "Authorization: Bearer $TOKEN" "$URL/slo/history?series=brief.p95&window=1h"`,
   which returns `{"enabled":true,...}` once the history has run one interval. The
   datasource's *Save & test* button was not verified against a bearer-gated base URL
   that has no `/` route; do not rely on it.

Rollback: delete the provisioning files and restart Grafana. The substrate side is
`SUBSTRATE_METRICS_HISTORY_SERIES=core` (or unset) and a restart.

## Regenerating, and the drift lock

```sh
bun run dashboards:build            # writes infra/vps/dashboards/
bun scripts/dashboards.ts --check   # renders in memory, diffs, exits 1 on drift
bun scripts/dashboards.ts --out DIR # another directory
```

`--check` exits 0 when every generated file is byte-identical to the one on disk and
no other file sits in the directory; it prints each missing, out-of-date or unexpected
file and exits 1 otherwise. The write mode replaces files through a temporary name and
a rename, and never deletes one. The output is deterministic: keys sorted, panel ids
counting from 1, fixed uids and `schemaVersion`.

`scripts/dashboards.test.ts` (part of `bun test`) fails when

- a catalogue target, a threshold default or the allow-list changes and the committed
  files were not regenerated;
- a series of the allow-list has no panel;
- an objective is added to `sloCatalogue()` without a decision in `SLO_SERIES` (a chart
  series, or `null` for a text panel);
- a panel's unit, label or series name disagrees with the series' own spec, a
  datasource reference does not resolve to the provisioning example, a panel id repeats,
  a window or step variable is a value the route would refuse, or a provisioning
  example carries a scheme, a host or a token-shaped assignment.

## What this does not do

- It does not draw `lease.steal_rate` or `quarantine.rate`: no durable series exists
  for them, so they are text panels pointing at `GET /slo`.
- It does not alert. Alerting stays with `/slo` and the notifier.
- It does not read the server's `SUBSTRATE_SLO_*` overrides.
- It was not rendered by a live Grafana in this change: the JSON is checked for shape
  and references by the test, and the first import is the first rendering. If Infinity
  rejects a field, the generator is the one place to fix it.
